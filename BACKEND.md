# Backend Hope: IR → `.hbc`

Backend собирает стековый `IrProgram` в переносимый двоичный HBC v1.
Публичный API: `HbcBackend.compile(program)` → `HbcModule`,
`compileToBytes(program)` → `ByteArray`, `write(program, path)` → модуль и файл.
Номера опкодов и двоичная раскладка v1 сохранены.

В репозитории есть грамматика Hope и семантические заготовки, но пока нет актуального
AST и перехода из дерева разбора в IR. Поэтому это **IR → bytecode backend**,
а не полный компилятор исходного текста. Старые `.deprecated`-файлы относятся к другой грамматике.
Проверка типов, разрешение имён, распределение локальных слотов и понижение AST в IR
должны выполняться frontend'ом до вызова backend.

## Запуск и пример

Нужен JDK 21 и `JAVA_HOME`, указывающий на него. Команды выполняются из каталога,
содержащего `build.gradle.kts`:

```powershell
.\gradlew.bat test
.\gradlew.bat run --args="--demo build/example.hbc"
.\gradlew.bat run --args="--dump build/example.hbc"
```

В этой рабочей копии для проверки подготовлен локальный JDK (без системной установки).
Если `java` отсутствует в PATH, в текущем PowerShell можно использовать его и готовый кэш:

```powershell
$env:JAVA_HOME = (Resolve-Path '.tools/jdk-21.0.12.1+1').Path
$env:GRADLE_USER_HOME = Join-Path (Get-Location) '.tools/gradle-user-home'
```

Папка `.tools/` исключена из Git и не является частью исходников.

`--demo` создаёт функцию `sumTo(n)`, суммирующую `1..n` циклом (для `n <= 0` возвращает 0).
Исходный IR находится в `BackendExample.kt`. `--dump` читает, проверяет и дизассемблирует
файл: выводит константы, функции, байтовые адреса инструкций и адреса переходов.
CLI пока не принимает исходный текст Hope и не исполняет программу.

Минимальная интеграция из Kotlin:

```kotlin
import java.nio.file.Path
import lv426.compiler.backend.*

val program = IrProgram(listOf(IrFunction(
    name = "answer",
    parameterCount = 0,
    localCount = 0,
    instructions = listOf(
        IrInstruction.Push(HbcConstant.IntValue(42)),
        IrInstruction.Return(hasValue = true)
    )
)))
HbcBackend.write(program, Path.of("build/answer.hbc"))
```

`HbcReader.read(bytes)` восстанавливает модуль. `HbcDisassembler.disassemble(module)`
или `disassemble(bytes)` возвращает текстовый листинг. `HbcVerifier.validate(module)`
можно вызвать явно; compile, reader и сериализация используют его автоматически.

## Контракт IR и VM

Каждая функция начинает работу с пустым стеком операндов. `localCount` включает параметры:
аргументы лежат в слотах `0 until parameterCount`, остальные слоты выделяет frontend.
Их инициализацию перед чтением проверяет frontend. Глобальные значения доступны по имени
через хранилище VM; объявления и инициализацию глобальных переменных frontend должен
понизить в соответствующие операции.

Аргументы вызова и события кладутся на стек слева направо. `CALL` снимает `argc` значений
и **всегда кладёт один результат**; для `void` VM должна положить специальное значение unit.
Вызов как отдельный statement завершается `Pop`, даже если функция возвращает `void`.
`EMIT` снимает аргументы и не кладёт результат; порядок/время обработки события определяет host.
Имена функций внутри модуля уникальны, рекурсия и вызовы вперёд разрешены.
Если имя `CALL` отсутствует в таблице функций, это внешний вызов: host обязан разрешить
его и проверить сигнатуру перед исполнением. Backend не может отличить опечатку от такого импорта.

Бинарная операция снимает сначала правый, затем левый операнд и вычисляет `left op right`.
`AND`/`OR` вычисляют оба операнда. Для короткого замыкания frontend генерирует ветвления.
`JumpIfFalse` **снимает** булево условие при любом результате. `Return()` требует пустой
стек, `Return(true)` — ровно одно возвращаемое значение. Остаток стека при возврате запрещён.

`IrLabel` не занимает места в файле; метки локальны функции и определяются ровно один раз.
Переход записывается как знаковое `i32`-смещение от конца инструкции:
`target = instructionOffset + 5 + displacement`. Цель должна быть началом реальной
инструкции, а не позицией после последнего байта. Все достижимые пути должны завершаться
возвратом либо продолжаться переходом; бесконечный цикл с постоянной высотой стека допустим.

Backend проверяет структуру и высоту стека, но не типы значений. Например, недопустимую
арифметику над строкой и bool должен отклонить семантический анализатор. Размеры массивов,
структуры, enum и регистрация обработчиков `on/every/at` не имеют отдельного представления
в HBC v1; полноценная поддержка этих конструкций требует расширения IR/формата и VM.
Исполняющей production-VM в этом модуле нет; небольшой интерпретатор в тестах проверяет
выполнение циклов, рекурсии, аргументов вызовов и событий.

## Двоичный формат v1

Все многобайтовые числа — **big-endian**. `u16` — беззнаковое двухбайтовое число.
Индексы таблиц начинаются с нуля. Пул констант дедуплицируется в порядке первого появления,
поэтому одинаковый IR даёт одинаковые байты.

```text
magic:          4 bytes = 48 42 43 00 (HBC\0)
version:        u16 = 1
constantCount:  u16
constants:      constant[constantCount]
functionCount:  u16 (1..65535)
functions:      function[functionCount]

function:
  nameConstant:   u16 (индекс непустого строкового имени)
  parameterCount:u16
  localCount:    u16 (>= parameterCount)
  codeSize:      i32 (1..2^31-1, дополнительно ограничен памятью JVM)
  code:          byte[codeSize]
```

| Тег константы | Значение |
|---|---|
| `01` | `int`: знаковый i64 |
| `02` | `real`: IEEE 754 binary64 |
| `03` | `bool`: ровно один байт `00` или `01` |
| `04` | `string`: u16 длина **в байтах**, затем строгий UTF-8 |
| `05` | `time`: знаковый i64, миллисекунды |

Предел пула — 65535 записей, строки — 65535 байтов UTF-8. Некорректные Unicode-последовательности
отклоняются при чтении и записи. Неизвестные версии, теги, опкоды и лишние байты после таблиц запрещены.

В таблице инструкций числа опкодов шестнадцатеричные, `→` обозначает замену элементов вершины стека:

| Опкод | Инструкция | Операнды в файле | Стек |
|---|---|---|---|
| `00` | NOP | — | без изменений |
| `01` | PUSH_CONST | u16 index | → value |
| `02`, `03` | LOAD_LOCAL, STORE_LOCAL | u16 slot | → value / value → |
| `04`, `05` | LOAD_GLOBAL, STORE_GLOBAL | u16 name | → value / value → |
| `10`, `11` | NEGATE, NOT | — | value → result |
| `20`..`24` | ADD, SUBTRACT, MULTIPLY, DIVIDE, MODULO | — | left, right → result |
| `30`..`35` | EQUAL, NOT_EQUAL, LESS, LESS_OR_EQUAL, GREATER, GREATER_OR_EQUAL | — | left, right → bool |
| `36`, `37` | AND, OR | — | left, right → bool |
| `40` | JUMP | i32 displacement | без изменений |
| `41` | JUMP_IF_FALSE | i32 displacement | condition → |
| `50` | CALL | u16 name, u16 argc | args → result/unit |
| `51` | EMIT | u16 name, u16 argc | args → |
| `60` | RETURN | — | пустой стек; возврат unit вызывающему |
| `61` | RETURN_VALUE | — | value →; возврат value вызывающему |
| `62` | POP | — | value → |

Все `name`-операнды ссылаются на непустую строку пула.

## Проверки и запись

Общий verifier проверяет таблицы, UTF-8, имена, кадры функций, константные ссылки,
локальные слоты, полные инструкции, цели переходов и число аргументов внутренних вызовов.
Структура проверяется даже для недостижимого кода. Для достижимого кода обход графа
управления обнаруживает нехватку операндов, разные высоты стека на слиянии ветвей,
накопление стека в цикле, некорректный возврат и выход за конец функции.
Ошибки байткода дают `HbcFormatException` с контекстом функции/инструкции; ошибки входного
IR также могут давать `IllegalArgumentException`.

Генератор исправляет все метки одним проходом по одному буферу, без копии функции для
каждого перехода. Запись полностью проверяет и сериализует модуль до изменения выходного
файла, затем пишет временный файл рядом и заменяет целевой. Замена атомарна при поддержке
файловой системой; иначе используется обычная замена. Временный файл убирается после операции.

Тесты включают эталонные байты HBC v1, прямые/обратные и длинные переходы,
дедупликацию, round-trip, повреждённые файлы, проверки стека, сохранность старого файла
при ошибке компиляции и исполнение результатов генерации тестовым интерпретатором.
